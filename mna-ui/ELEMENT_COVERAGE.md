# Chat element coverage

The preparation flow adds a header action menu, accessible nested setup/source dialogs, input chips with a pinned index, raw source checkboxes and actual coverage, inline PitchBook/ROGO upload staging, editable output schema and prompt, model/deployment and batch controls, a real data preview, approval state, saved setup cards, and version-edit actions. Workspace-origin results are appended to the same mounted assistant-ui thread without replacing its composer or restoring abandoned branches. Real preparation and import calls also appear in Session log. The model execution stage remains disconnected; the offline LangGraph scaffold is documented separately.

This inventory describes the current local chat implementation in `src/chat/ChatThread.tsx`, `src/chat/ArtifactCard.tsx`, `src/chat/MarkdownMessage.tsx`, `src/chat/SessionTiming.tsx`, `src/SessionLog.tsx`, `src/App.tsx`, and `src/lib/chat-driver.ts`, `chat-jobs.ts`, `chat-store.ts`, and `session-store.ts`.

“Runtime-connected” means the control or display is wired to this app’s current state or callback. It does not imply an external model, provider, or agent service is connected. “Integration boundary” marks concepts whose provider-backed behavior is unavailable. There is no private reasoning display; plans, tool calls, statuses, and recorded results are the public workflow shown to the analyst.

## Component boundaries

The chat shell uses assistant-ui runtime primitives for messages, the composer, attachments, queue items, edit/action bars, branches, error states, and thread scrolling. `MarkdownMessage` uses assistant-ui’s Markdown primitive. The tool-call disclosure and grouped tool timeline are app renderers attached to those primitives.

Criteria, company results, recommendations, local jobs, checkpoints, memory/context, and provider handoffs are custom domain cards in `ArtifactCard`. They follow patterns from the [assistant-ui Elements catalog](https://www.assistant-ui.com/elements), but they are not the catalog’s shadcn-installed components. The custom `SessionTiming` and `SessionLog` use this app’s event records.

The session log is a browser-local turn ledger with event details, search and kind/status filters, selectable timing spans, follow-latest, and Markdown/JSONL/ZIP exports. Mobile uses Activity and Record details modes. It is not a DeepSeek Harness session runtime. The [DeepSeek Harness core documentation](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/core.md) describes an event-sourced agent loop and session model; its [subagent subsystem](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/subagent.md) describes actual delegated-agent orchestration. This application has neither Harness integration nor connected external subagents. Its local ledger does not implement Harness event semantics, nested session trees, or full span virtualization.

The ZIP export includes every session event, even when visible event filters are active, and declared upload bytes by fetching them from the local file endpoint while the local server still has them. It preserves the exact original bytes. If a file is no longer available or the server is offline, ZIP creation fails with an actionable message; Markdown and JSONL retain the session’s recorded history without original upload bytes.

## Manual demo path

Use the current local app with the Rust service available. The sample company data is fictional; the tool calls are real local Rust calls.

1. Choose **New screening**, then select **Run the example** or type `/example`. Review the generated criteria card.
2. Select **Approve criteria**. The local search starts. Expand tool calls in the chat or open **Session log** to inspect actual calls, arguments, results, and durations. Wait for the completed company and checkpoint artifacts.
3. After completion, inspect **Choose the next step**. **Not now** defers; **Prepare Bing research** leads to **Draft questions** but does not search the web. Choose **Add PitchBook data** to display the file handoff. Select **Add files**, attach `public/examples/pitchbook-mapping.csv` and `public/examples/pitchbook-data.xlsx`, then send. With a completed run and approved criteria, the local importer processes compatible files and records the result. `public/examples/rogo-data.xlsx` and `public/examples/criteria.txt` are also available.
4. Stage `criteria.txt` in Workspace and return to Chat to confirm its original file artifact remains available. Type `/memory` or choose a company from `@` suggestions to read its business description and expand **View saved context**.
5. Type `/flow` to see the process steps and diagram.
6. Type `/export` to open the session log. Select a timing span or switch its range from **Selected turn** to **All events**; mobile provides **Activity** and **Record details** modes. Export Markdown or JSONL for the recorded ledger, or **Full ZIP** to include every event and exact original upload bytes still available from the local server.

These steps describe the implemented path. Recorded browser checks and their remaining limits are listed in [VALIDATION.md](VALIDATION.md).
